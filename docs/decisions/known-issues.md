# 边界情况与已知限制

## 边界处理

| 场景 | 处理 |
|---|---|
| `session.error` 与 `message.updated(error)` 同时到达 | `pendingContinue` 去重，只在 idle 时统一发送 |
| 会话运行中收到错误/空闲 | 忙 / 活跃状态由**事件派生**（`lastBusyAt` 60 秒窗口、`lastActiveAt` `idleDelayMs` 窗口），判定为忙或仍在活动时**跳过本轮注入**，到期再判定；事件未带 status / outcome 时，走 **idle 时钟兜底**（`session.idle` 到达即排一次延迟注入）。**不存在 `session.status` 查询或轮询等待** |
| 当天已过 endTime 才 on（**非**跨午夜窗口） | watch 时冻结 endAt，立即停止值守，不滚动到次日 |
| 用户主动中止 | `session.execution.interrupted`（V2）/ `session.idle` 且 `outcome="interrupted"`（V1，Esc 手工停止）→ 停止但保留值守标记（可重新 on）。`MessageAbortedError` / `operation was aborted` 属 `excludePatterns`（不自动续跑的错误特征），并非停止来源 |
| 服务重启 | storage 仍在，内存态（定时器/在途）丢失，从 storage 恢复值守列表 |
| 插件卸载/热重载 | cleanup 返回 dispose：拆定时器、退订、注销 slot |
| 跨午夜值守窗口 | 自动滚动到次日（22:00→08:30 在 23:00 开启不会立即停止）；次日 `00:00`..`startTime` 之间窗口仍视为开启（`startGateClosed`，v0.5.1） |
| 空完成标记配置 | `completionMarkers: []` 不检测完成，会话持续值守（不会瞬间判完成） |
| 单引号 JSONC 配置 | 解析器按**字面量语义**解析（v0.5.6 起）：只有 `\'` → `'`、`\\` → `\` 是转义，其它 `\X` 原样保留。Windows 路径如 `'C:\Users\<用户名>\name\file.txt'` 原样生效；需要 JSON 转义语义（真换行等）时用双引号写 |
| 纯 5xx 裸状态错误 | 匹配串含 `(status: N)`，`"(status: 5"` 可命中 5xx；裸 `"5"` 已于 v0.2.2 收紧为 `"(status: 5"`，`"429"` 命中 429 |
| 配置里的空字符串 | 6 个数组型配置键（`completionMarkers` / `errorPatterns` / `excludePatterns` / `excludeTitleKeywords` / `escalationPressureLadder` / `frustrationTriggers`）统一**剔除空串**（v0.5.5）——空串是任何字符串的子串，留着会让匹配器命中一切 |

## 已知限制

1. 不做 AI 判断"任务是否完成"——用完成标记 + 最大次数兜底，可能误判（完成标记未命中时靠次数/时段停止）（v0.2.0 起）
2. `session.error` 事件载荷形状随版本变动，双兼容解析 + 单测锁定当前版本，宿主升级后需回归（v0.3.11 起；当前宿主 V2 schema 已无该事件，此处指有意保留的 V1 兼容路径）
3. retry hook 的错误分类依赖 opencode 判定，仅影响单次模型调用；最终失败仍走续跑兜底（v0.2.0 起）
4. 插件需 opencode 服务存活；服务重启后定时器/在途态丢失，从 storage 恢复值守名单（v0.2.0 起）
5. 值守范围只限用户主动 `/autocontinue on` 的会话，不做全局自动跑（v0.2.0 起）
6. **验证输出反射（部分缓解）**：assistant 若逐字引用不可信的验证命令输出（其中可能含哨兵/完成标记文本），该文本会被反射进控制流——哨兵/完成标记检测只读 assistant 消息文本，无法区分「模型自己说的」与「模型转述的验证输出」。verify 模式把完成判定绑定到命令 exit code，部分消解该风险；非 verify 模式仍以文本标记为准。完整缓解需要脆弱的启发式，故不引入（v0.4.0 起）
7. **事件路径不判哨兵（延迟，非漏判）**：assistant 事件路径不评估哨兵（`<loop-abort>` / `<loop-pause>`），依赖随后的 `session.idle` 经 `maybeInject` 兜底，最多延迟一个 `intervalMs`（默认 1h）；完成检测同样靠 idle → `maybeInject` 复查兜底（v0.4.0 起，v0.5.0 扩到 abort/pause 哨兵）
8. **挫败感触发是启发式（P2，v0.5.2）**：`frustrationTriggers` 对真实用户消息做**大小写不敏感的子串**匹配，可能**误判**（正常抱怨被当成质量不满）或**漏判**（换一种说法表达不满）。默认关闭（`frustrationTriggers: []`），词表需用户自行维护
9. **上界可被显式关闭（P3，v0.5.2）**：`watchTimeoutMs: 0` / `verifyMaxIterations: 0` 仍表示无限；默认值已改为 24h / 50，但显式写 `0` 可恢复无限值守，误配置时需要留意
10. **停止原因粒度**：`stopReason` 只说明「为什么停」，不说明「任务是否真的完成」；被护栏停掉的任务仍需人工确认（v0.5.2）
11. **24h 默认墙钟上限会结束长值守**：`watchTimeoutMs` 自 v0.5.2 起默认 24h，长任务（如跨天批量处理）会在 24h 后被停掉，需显式写 `watchTimeoutMs: 0` 恢复无限。v0.5.3 起该预算**按轮次**计量（真实用户消息开启新一轮即重算），此前按首次 `/autocontinue on` 累计（v0.5.2 / v0.5.3）
12. **Windows 上本地 `file://` 注册路径格式**：必须是三斜杠 + 正斜杠（如 `file:///D:/path/to/repo`），写成两斜杠或反斜杠会加载失败；终端用户推荐用 `opencode plugin add github:dubuqiangu/opencode-autocontinue` 而非本地路径注册（v0.2.0 起）
13. **回声时间窗兜底的残留风险（v0.5.5）**
    - **触发条件**：真实用户消息落在 `selfEchoWindowMs`（默认 10s）窗口内，**且**宿主不提供可提取文本（入站消息取不到 `payload.text` / 文本 part）。
    - **后果**：该消息被回声兜底判为「自身回声」而**未被处理**——既不触发 `resume()`（新一轮不开启），也不进入挫败感检测等真实用户路径，用户的输入被静默吞掉。
    - **当前是否可绕过**：只能**部分**绕过——调小 `selfEchoWindowMs` 缩短暴露窗口；也可改用与用户输入无关的通道（完成标记 / 哨兵）表达意图。但只要宿主不提供可提取文本，引擎就没有可比对的依据，无法从根本上避免。
    - **计划**：本版**不修**（彻底修复依赖宿主侧提供稳定的入站文本，属于宿主行为变更）；作为已知限制长期记录，后续随宿主 API 演进复评。
14. **存储多实例丢行（v0.5.5 已知，本版不修）**
    - **触发条件**：同一台机器上**同时存在多个插件实例**（例如同时开着两个 opencode 进程 / 两个 TUI），且它们都对同一份 watched 列表做写入。
    - **后果**：值守列表按**单一存储键** `opencode-autocontinue.watched` 保存，多实例并发写会**互相覆盖**——后写入的一方用自己内存里的整份快照盖掉前一方刚写入的条目，导致**丢行**（某个会话的 `watched` 记录凭空消失）。
    - **当前是否可绕过**：**不能**在插件内绕过——读取与写入都是整份列表，读-改-写之间没有跨实例的锁。
    - **计划**：本版**不修**——按会话分键（每个会话一个存储键）属于**破坏性存储布局变更**，会改变既有 `opencode-autocontinue.watched` 的内容结构，波及升级路径与旧记录迁移。留待后续版本单独决策（届时需给出迁移与向后兼容方案）。
15. **跨午夜时间窗口语义未做实机验证（v0.5.3 起未变）**
    - **触发条件**：配置 `startTime` 22:00 / `endTime` 08:30，在真实会话中跨过 `00:00` 后触发注入判定。
    - **后果**：若 `computeEndAt` 的跨日滚动或 `startGateClosed` 的跨夜感知与真实宿主时间行为不符，会出现「本该继续注入却立即停止」或「窗口已过却继续注入」。
    - **当前是否可绕过**：可——把窗口写成**非**跨午夜（如 08:00→20:00）即可绕开跨夜分支，代价是失去夜班场景。
    - **计划**：单测与静态守卫已覆盖（`computeEndAt` / `startGateClosed` 的边界用例），但**未做实机验证**；待宿主实机确认后再关闭本条。
16. **验证流程的 TOCTOU（检查与使用之间的时序）竞态未做实机验证（v0.5.3 起未变）**
    - **触发条件**：验证命令执行期间用户发来真实消息（或在 await 窗口内关闭值守）。
    - **后果**：若 await 前后的复检不足，**陈旧的验证结果**会被当成新一轮的结果——可能误判 `done`（任务其实没完成）或误注入。
    - **当前是否可绕过**：**不可**——这是引擎内部的时序，用户无从干预；只能靠实现层的快照复检 + `roundId` 比对兜底。
    - **计划**：实现层已加固（命令前快照复检、await 后 staleness 复检、`roundId` 进程级全局单调递增、final-check 复检），但**未做实机验证**；待实机确认后再关闭本条。
17. **`stopReason` 在 footer 与 toast 中的实际渲染未做实机验证（v0.5.3 起未变）**
    - **触发条件**：会话因护栏停止（如 `injection-cap` / `verify-limit`），观察 footer `[AC ⏹ N · <phrase>]` 与 `/autocontinue status` toast 的正文。
    - **后果**：若文案或格式与预期不符（例如原因短语缺失、toast 正文与 footer 不一致、计数未按 `1 injection` / `N injections` 复数化），用户看到的「为什么停了」就是错的或空的。
    - **当前是否可绕过**：可——直接查服务端状态或 RPC `status` 输出里的 `stopReason` 枚举值。
    - **计划**：**未做实机验证**；待宿主实机确认渲染后再关闭本条。
